# S0-025: acertar o CHECK pedido_pagamento_completo (0037) no COERENCIA_DA_FK para as FKs pedido_forma_pagamento_fk e pedido_prazo_pagamento_fk

## Contexto
CI do lote verificacao/lote-t0089 (run 42331525920), tests/integracao/multitenant/vazamento-escrita.test.ts > "em cada FK composta, apontar uma linha de A para a linha-mãe de B é recusado (23503)":
`pedido_forma_pagamento_fk: new row for relation "pedido" violates check constraint "pedido_pagamento_completo": expected '23514' to be '23503'`.

As FKs novas da 0037 (db/migrations/0037_forma_prazo_escalonada.up.sql) JÁ SÃO COMPOSTAS com tenant_id (o 1º caso do describe, "toda FK ... é composta", passou):
- vendedor.pedido: pedido_forma_pagamento_fk (tenant_id, forma_pagamento_id) -> vendedor.forma_pagamento (tenant_id, id); pedido_prazo_pagamento_fk (tenant_id, prazo_pagamento_id) -> vendedor.prazo_pagamento (tenant_id, id);
- prazo_pagamento_forma_fk (tenant_id, forma_pagamento_id) -> vendedor.forma_pagamento (tenant_id, id);
- tabela_escalonada_tabela_fk (tenant_id, tabela_preco_id) -> catalogo.tabela_preco (tenant_id, id).

O que reprova é o CHECK pedido_pagamento_completo da 0037: num_nulls(forma_pagamento_id, prazo_pagamento_id, forma_pagamento_codigo, forma_pagamento_nome, prazo_codigo, prazo_descricao, prazo_parcelas_dias, prazo_medio_dias) in (0, 8) — os 8 vêm juntos ou nenhum (§4.1 do docs/desenho/T-0089.md). Nenhum pedido da fixture dois-tenants leva pagamento (de propósito: pedidos do APK antigo), então o UPDATE de só uma coluna dá 23514 antes da FK (23503). É exatamente o caso do COERENCIA_DA_FK. A 0037 e a fixture ficam como estão (CHECK é regra; não há CHECK adiável no Postgres).

## O que preciso
Em tests/integracao/multitenant/vazamento-escrita.test.ts, acrescentar ao COERENCIA_DA_FK (texto pronto; coalesce mantém o que já houver; subconsulta roda como macuxi_app no contexto de A, então pega a linha de A; [0] com médio 0 passa em vendedor.parcelas_validas e vendedor.prazo_medio_coerente):

```ts
  // 0037 (T-0089) pedido_pagamento_completo: forma, prazo e os 6 retratos do pagamento vêm juntos ou nenhum (num_nulls in (0, 8));
  // a fixture não leva pagamento em pedido, então completa-se a linha com o prazo/forma de A e o retrato "À vista" [0]
  pedido_forma_pagamento_fk:
    "prazo_pagamento_id = coalesce(prazo_pagamento_id, (select p.id from vendedor.prazo_pagamento p order by p.id limit 1)), forma_pagamento_codigo = coalesce(forma_pagamento_codigo, 'AVISTA'), forma_pagamento_nome = coalesce(forma_pagamento_nome, 'À vista'), prazo_codigo = coalesce(prazo_codigo, 'AVISTA'), prazo_descricao = coalesce(prazo_descricao, 'À vista'), prazo_parcelas_dias = coalesce(prazo_parcelas_dias, '{0}'::int[]), prazo_medio_dias = coalesce(prazo_medio_dias, 0)",
  pedido_prazo_pagamento_fk:
    "forma_pagamento_id = coalesce(forma_pagamento_id, (select f.id from vendedor.forma_pagamento f order by f.id limit 1)), forma_pagamento_codigo = coalesce(forma_pagamento_codigo, 'AVISTA'), forma_pagamento_nome = coalesce(forma_pagamento_nome, 'À vista'), prazo_codigo = coalesce(prazo_codigo, 'AVISTA'), prazo_descricao = coalesce(prazo_descricao, 'À vista'), prazo_parcelas_dias = coalesce(prazo_parcelas_dias, '{0}'::int[]), prazo_medio_dias = coalesce(prazo_medio_dias, 0)",
```
(Cada string não repete a coluna da própria FK — o teste já faz `set "<coluna>" = $2`; repetir daria 42601.) prazo_pagamento_forma_fk e tabela_escalonada_tabela_fk não precisam de acerto (sem CHECK amarrado à coluna da FK).
