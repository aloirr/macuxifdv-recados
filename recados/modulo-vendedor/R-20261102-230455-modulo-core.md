# T-0061 Core: nomes finais de endereços de entrega e unidades de venda

## Contexto
T-0061 (RF-CORE-12, RN-VEN-15, RN-VEN-17). Contratos do Core para endereços de entrega e unidades de venda já estão em `modules/core/contracts` (branch nuvem/T-0061-core-enderecos-unidades). Tudo aditivo, nada do @1 muda. Os schemas de pull e a `core.cadastro_resumo@1` já existiam; o que muda agora são as funções públicas de leitura offline e o Cliente 360.

## O que preciso / o que mudou
Nomes FINAIS (importe de `@macuxi/core/contracts`):
1. Pull (entidades do motor, escopo e nome no `motor.linhas`): `cliente_endereco` (escopo carteira; `ClienteEnderecoSyncSchema` / tipo `ClienteEnderecoSync`: id, cliente_id, tipo 'principal'|'entrega'|'cobranca', descricao, logradouro, numero, complemento, bairro, cidade, uf, cep, latitude, longitude, principal, ativo, deleted_at) e `produto_unidade` (escopo tenant; `ProdutoUnidadeSyncSchema` / `ProdutoUnidadeSync`: id, produto_id, unidade, fator, ean, padrao, ativo, deleted_at). Ex.: `motor.linhas<ClienteEnderecoSync & LinhaSync>('cliente_endereco')`, como o Catálogo faz com 'produto'. O servidor já filtra pela carteira; o Vendedor NÃO lê tabela do Core.
2. Funções puras de leitura offline (em `contracts/enderecos.ts`, sem rede, sem React):
   - `enderecosDeEntrega(linhas, clienteId)` -> `EnderecoDoCliente[]`: só ativos e vivos do cliente, SEM cobrança, o padrão PRIMEIRO; cada item = a linha + `padrao: boolean` + `resumo: string` (linha única "Rua A, 10 - Centro - Boa Vista/RR - CEP 69300-000"). RN-VEN-17: o pedido usa `enderecos[0]` (padrão) quando o vendedor não escolher; se vazio, não há endereço (cliente sem endereço do ERP).
   - `enderecoPadrao(linhas)`: o `principal` ativo; sem principal, o primeiro de entrega ativo (ordem estável); cobrança nunca é padrão; `null` se não houver.
   - `listarEnderecosDoCliente(linhas, clienteId, { incluirCobranca? })`, `resumoDoEndereco(e)`, `formatarCep(cep)`.
   - `unidadesDoProduto(linhasUnidade, produtoId, unidadeBase)` -> `UnidadeDoProduto[]`: ativas e válidas, a PADRÃO primeiro, depois por fator; cada item = linha + `rotulo` ("UN", "CX c/ 12"). Produto sem linha devolve 1 item sintético (unidade base, fator 1, id `base:<produtoId>`: use a SIGLA `unidade`, nunca esse id, no pedido).
   - `unidadePadraoDoProduto(linhas, unidadeBase)` -> `{ unidade, fator }` (a marcada; senão a base com fator 1), `rotuloDaUnidade(unidade, fator)`, `fatorValido(n)` (inteiro > 0).
3. Cliente 360 (GET /v1/core/clientes/:id e ficha offline do app): `Cliente360.enderecos` (ClienteEnderecoSync[] ativos, padrão primeiro) e `Cliente360.endereco_padrao_id` (uuid|null), ambos opcionais.
4. `core.cadastro_resumo@1` inalterada (já devolve `produtos[].unidades` e `enderecos`; o principal do cliente vem sempre). A API do pedido valida `endereco_entrega_id` contra `enderecos[]` por `endereco_ids` e `unidade` contra `produtos[].unidades`.
5. Eventos que o Core consome (nada para o Vendedor fazer): integracao.produto_unidade.atualizado@1 -> core.produto_unidade; integracao.cliente_endereco.atualizado@1 -> core.cliente_endereco (no máximo 1 unidade padrão e 1 endereço principal vivos; ao marcar um novo, o anterior é desmarcado).

## Pronto quando
Você consegue listar endereços e unidades offline só com estas funções e entidades. Se algum nome atrapalhar a T-0053, me avise antes de eu fechar (entrego até o fim da tarefa; sem mudança de nome prevista).
