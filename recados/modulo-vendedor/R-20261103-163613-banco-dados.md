## O que preciso
Usem estes nomes exatos (dicionário: docs/banco/vendedor.md e docs/banco/catalogo.md, seção 0020):

**vendedor.pedido** (Drizzle `pedido` em modules/vendedor/db/nuvem.ts)
- `desconto_valor_cents` bigint not null default 0 · `acrescimo_valor_cents` bigint not null default 0 — R$ do ajuste do PEDIDO, sobre o total dos itens (digitado ou derivado do %)
- `ajuste_em` text not null default 'pct' ∈ ('pct','valor') — `MODOS_AJUSTE` exportado do nuvem.ts
- CHECKs: `pedido_ajuste_valor_nao_negativo`, `pedido_ajuste_valor_exclusivo` (desconto OU acréscimo em R$), `pedido_ajuste_sentido_coerente` (desconto em R$ exige acrescimo_pct = 0; acréscimo em R$ exige desconto_pct = 0), `pedido_ajuste_em_valido`
- índice `pedido_orcamento_aberto_ix (tenant_id, vendedor_id, orcamento_validade) where tipo = 'orcamento' and convertido_em is null and deleted_at is null` (lista de Orçamentos e janela do pull, §1.4 b)

**vendedor.pedido_item** (Drizzle `pedidoItem`)
- `desconto_unitario_cents` bigint not null default 0 · `acrescimo_unitario_cents` bigint not null default 0 — por unidade da MEDIDA VENDIDA, SEMPRE gravado (digitado, ou tabela − final no modo %)
- `ajuste_em` text not null default 'pct' ∈ ('pct','valor')
- CHECKs: `pedido_item_ajuste_valor_nao_negativo`, `pedido_item_ajuste_valor_exclusivo`, `pedido_item_ajuste_sentido_coerente` (contra desconto_pct/acrescimo_pct do item), `pedido_item_desconto_unitario_ate_tabela` (desconto_unitario_cents <= preco_tabela_cents), `pedido_item_ajuste_unitario_coerente` (com R$ gravado: preco_unitario_cents = preco_tabela_cents − desconto_unitario_cents + acrescimo_unitario_cents; item 0/0 fica fora), `pedido_item_ajuste_em_valido`
- modulo-vendedor: o receber precisa gravar os 3 campos coerentes com preco_unitario_cents (senão 23514); `desconto_pct`/`acrescimo_pct` seguem com o % (equivalente 2 casas no modo valor). Linhas anteriores ficam 0/0/'pct'.

**catalogo.produto_relacao** (Drizzle `produtoRelacao` + `TIPOS_RELACAO_PRODUTO_BANCO` em modules/catalogo/db/nuvem.ts)
- colunas: `id, tenant_id, produto_id uuid not null, relacionado_id uuid not null, tipo text not null, ordem integer not null default 0, ativo boolean not null default true, created_at, updated_at, deleted_at, external_id`
- sem FK para core.produto; CHECKs `produto_relacao_tipo_valido` ('complementar','superior','substituto' = TIPOS_RELACAO_PRODUTO do contrato, conferido em teste) e `produto_relacao_nao_e_de_si`
- únicos: `produto_relacao_uk (tenant_id, produto_id, relacionado_id, tipo) where deleted_at is null` (atende o `produto_id = any(...) and tipo in (...)` da api/sugestoes.ts) e `produto_relacao_external_uk`; sync `produto_relacao_sync_ix (tenant_id, updated_at, id)`; RLS isolamento_tenant + force; grant select/insert/update/delete; gatilho `produto_relacao_updated_at`
- modulo-catalogo: o provedor de pull em api/sync.ts (colunas produto_id, relacionado_id, tipo, ordem, ativo) já casa com o banco. Fixture dois-tenants (grupo 0x4e): A tem 4 linhas (p1→p2 complementar REL-A-1, p2→p1 substituto, p1→p2 superior INATIVA, p2→p1 complementar APAGADA) e B 1 linha (relacionado fora da carga, sem FK).
