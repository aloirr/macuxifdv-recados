# T-0089: API exata de core.financeiro_cliente@1 e dos 2 campos do cliente

## Contexto
T-0089, fatias C1/C2 do Core prontas em `modules/core`. API exata para o card "Crédito do cliente" e a RN-VEN-25.

## O que preciso
1. **Consulta `core.financeiro_cliente@1`**: importe `CONSULTA_FINANCEIRO_CLIENTE` de `modules/core/contracts` e liste em `usaConsultas`. Entrada `{ cliente_id: uuid }`. Saída `{ financeiro: null | { limite_cents, saldo_aberto_cents, credito_disponivel_erp_cents (null = calcule limite - saldo, RN-VEN-12), bloqueado, motivo_bloqueio, vencidos_qtd, vencidos_cents, maior_atraso_dias (0 sem vencido; RN-VEN-13), atualizado_erp_em (ISO ou null) } }`. `null` = cliente sem linha financeira ("Sem dados de crédito"). Na API use `tx.consultar`; no aparelho `ambiente.consultar` (lê `cliente_financeiro` e `titulo` locais; "hoje" no fuso do tenant; vale offline). A data da última sincronização vem de `motor.estado().sincronizado_em`, não da consulta.
2. **`core.cadastro_resumo@1`**: `clientes[]` ganha `prazo_medio_max_dias` (int >= 0 ou null = sem teto) e `formas_pagamento` (string[] de códigos ou null; null ou vazio = todas). Ausente = emissor antigo. O `ClienteSyncSchema` (pull) tem os mesmos 2 campos.
3. **Regras prontas** em `modules/core/domain/pagamento-cliente.ts` (testadas): `pagamentoPermitidoAoCliente` (RN-VEN-25), `exigeAprovacaoPorTituloVencido` (RN-VEN-13, padrão 5 dias) e `financeiroDoCliente`. Você não importa o `domain` do Core: duplique a regra no seu domain ou me peça para expor.
4. **Pendente do seu lado**: publicar em `modules/vendedor/contracts` a consulta `vendedor.formas_pagamento@1` (entrada `{}` strict; saída `{ formas: [{ codigo, nome, ativo }] max 200 }`) e oferecê-la na API. O Core já a lista em `usaConsultasOpcionais`; a lista de formas na ficha do cliente do BKO fica só leitura até o contrato existir.

## Pronto quando
O card Crédito do cliente e a revalidação RN-VEN-25 usam essa API, e o contrato `vendedor.formas_pagamento@1` está publicado.
