## Contexto
T-0029 onda 1, §10 do desenho. Migrações NOVAS (nenhuma aplicada foi editada), com `.down.sql`, testadas up/down/up com dados.

## O que foi feito (nomes exatos)
**0008_catalogo_preco** (schema `catalogo`, novo; RLS forçado, campos comuns, sync `(tenant_id, updated_at, id)`, sem FK para o Core):
- `catalogo.tabela_preco` (codigo único vivo, nome, ativo).
- `catalogo.tabela_preco_item` (tabela_preco_id FK composta, produto_id, preco_cents > 0, vigencia_inicio, vigencia_fim; fim > inicio; nulo = desde sempre / sem fim). Único vivo `tabela_preco_item_vigencia_uk (tenant_id, tabela_preco_id, produto_id, vigencia_inicio) NULLS NOT DISTINCT` (é o índice da consulta). Sobreposição não é barrada: vale o item vivo de maior início <= data.
- `catalogo.cliente_tabela_preco` (cliente_id, tabela_preco_id FK; uma viva por cliente).
- Drizzle: `modules/catalogo/db/nuvem.ts` (tabelaPreco, tabelaPrecoItem, clienteTabelaPreco). O contrato `ItemTabelaPreco` usa nomes em inglês: o provedor mapeia tabela_preco_id→price_table_id, produto_id→product_id, preco_cents→price_cents, vigencia_inicio→valid_from, vigencia_fim→valid_to. Consulta modelo em `docs/banco/catalogo.md`.

**0009_vendedor_pedido_completo**:
- `vendedor.pedido` + numero, hash_envio, cliente_resumo (jsonb objeto), cliente_nome, vendedor_nome, tabela_preco_id, condicao_pagamento_id (FK no schema), condicao_pagamento_descricao, nivel_aprovacao, motivos_aprovacao (text[] NOT NULL default '{}'), aprovacao_automatica (NOT NULL default false), decidido_por_id, decidido_em, motivo_rejeicao. CHECKs: pending_approval ⇒ nível; rejected ⇒ motivo com 3+ caracteres (btrim); nível ∈ NIVEIS_APROVACAO; motivos ⊂ MOTIVOS_APROVACAO; **hash_envio = sha256 em hex minúsculo (64)**. Índices `pedido_status_ix (tenant_id, status, created_at desc)` e `pedido_numero_uk (tenant_id, numero)`.
- `vendedor.pedido_item` + produto_sku, produto_nome, unidade.
- `vendedor.pedido_evento` (pedido_id FK composta, de, para, autor_id, autor_nome, autor_perfil, motivo, nivel, acima_do_nivel, ocorrido_em); de/para ∈ ORDER_STATUSES, de ≠ para; índice `(tenant_id, pedido_id, ocorrido_em)`. **A aplicação só tem SELECT e INSERT** (histórico não se edita).
- `vendedor.condicao_pagamento` (codigo único vivo, descricao, ativo, padrao; no máximo uma padrão viva, padrão ativa) e `vendedor.cliente_condicao` (par único vivo).
- **Número**: contador por tenant `vendedor.numeracao_pedido` (fora do sync) + função `vendedor.proximo_numero_pedido()` → '000001' (invoker, RLS, sem buraco, falha sem contexto). Chamar SÓ depois de saber que o pedido é novo, na mesma transação (ex.: insert … on conflict (id) do nothing returning id; se inseriu, update … set numero = vendedor.proximo_numero_pedido()).
- Dados antigos: pending_approval sem nível recebe o nível pela alçada padrão (≤10 supervisor, ≤15 gerente, acima analista) e {desconto}; rejected sem motivo recebe 'Rejeitado antes do registro do motivo.'.
- Drizzle: `modules/vendedor/db/nuvem.ts` (pedido, pedidoItem, pedidoEvento, condicaoPagamento, clienteCondicao, numeracaoPedido; listas de NIVEIS_APROVACAO/MOTIVOS_APROVACAO/ORDER_STATUSES).
