# Perfis de acesso no BKO: controle de senhas e de "quem pode o quê" fica na tela de perfil; todo usuário atrelado a um perfil

## Contexto
Resposta às premissas P2, P5–P8 do R-20261107-180311. Decisão minha: o controle de senhas e de quem pode o quê **não fica fixo no código**; ele é definido na área **Perfis de acesso** (onde ficam as permissões). Se essa página não existe por inteiro no BKO, crie. Pela esteira permanente, entra já.

## O que preciso / o que mudou
**1. Página "Perfis de acesso" no BKO (Core), editada pelo admin do cliente:**
- lista dos perfis do tenant; para cada perfil, as permissões agrupadas por área:
  - **Usuários e senhas:** criar usuário, editar, desativar, redefinir senha — e **de quais perfis** pode redefinir;
  - **Módulos** do perfil (o padrão por perfil do RF-CORE-03 passa a morar aqui);
  - **Ações** da matriz do doc 03 §2 (pedido, cancelar, aprovar até a alçada, metas, cadastros, catálogo, pesquisas, trilhas etc.) e os parâmetros que hoje já são do perfil (ex.: `promotor_ve_pedidos`, `promotor_ve_preco_estoque`);
  - **Escopo de dados** (carteira, equipe, tenant) e **onde entra** (app Campo, app Gestão, BKO, portal);
- valores iniciais = a matriz atual do doc 03 + as premissas P2, P5, P6, P7 e P8, mais: **o super-admin da Macuxi pode redefinir a senha do admin do cliente pelo portal**;
- perfis personalizados: o admin pode **criar um perfil a partir de um perfil base** (ex.: "Coordenador" a partir de Supervisor), herdando onde entra e o escopo, e ajustar as ações;
- toda alteração auditada (RN-AUD-01) e aplicada na próxima requisição (como a licença), sem novo login.

**2. Limites que a tela não deixa mudar (travados, mostrados com cadeado):**
- RN-CORE-33: vendedor, promotor e supervisor (e perfis derivados deles) **nunca** entram no BKO nem no portal;
- RN-PRO-01: promotor nunca cria/edita/cancela pedido;
- sempre existe pelo menos um admin ativo; o admin não tira de si mesmo a gestão de perfis e usuários (evita trancar a empresa);
- regra de senha RN-CORE-32 vale para todos.

**3. Todo usuário atrelado a um perfil:** criar usuário exige escolher o perfil (ou mais de um, pelo multiperfil aprovado no R-20261107-173950, item c); não existe usuário sem perfil. Confira a base atual e a demo: se houver usuário sem perfil, corrija na migração.

**4. Impacto na T-0094:** a T-0094 **não** grava as premissas como regra fixa no código: ela consulta as permissões do perfil (chaves como `usuario.criar`, `usuario.desativar`, `senha.redefinir` com a lista de perfis-alvo), com os valores iniciais acima. A página pode ser uma tarefa própria (ex.: T-0111) correndo em paralelo, mas o motor de permissões entra junto com a T-0094 para não precisar refazer.

**5.** Atualize RF-CORE-02/03 no doc 02 e o §2 do doc 03 (matriz vira "padrão de fábrica" editável, com os limites travados), e escreva a ADR se mudar o modelo de permissões do SDK.
