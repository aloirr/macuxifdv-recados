# Economia do Actions: PR só quando obrigatório, um push por PR, sem juntar o main sem conflito e outras regras

## Contexto
Ordem do dono do produto no chat com a ponte, 17/11, de manhã (Manaus): **"Preciso economizar no Actions. Diminua os PRs para fazer somente quando for de fato obrigatório. Avalie outras medidas para economizar e tome-as também."**

Consumo medido pela ponte (API do Actions, minutos por job arredondados para cima, como o GitHub cobra; o repositório é privado):
| Desde 15/11 | Runs | Minutos | Média |
|---|---|---|---|
| CI no push ao main | 47 | ~1.284 | ~27 (com código: 44 a 54 por merge) |
| CI no PR | 153 | ~966 | ~6 |
| **Só o dia 16/11** | | **~2.194** | |

- **O que mais pesa:** cada merge com código dispara as suítes completas no main (~50 min). Merge só de documentação custa ~3 a 4 min.
- **O que se perde à toa:** vários pushes no mesmo PR, chegando a 8 runs num branch só (`nuvem/v1014-parametros-modulo-core`). E o build do Android falhou duas vezes em 14 e 15/11, cerca de 120 min perdidos.

## Regras novas (valem a partir deste recado, para todos)
1. **PR só quando é obrigatório:** mudança de código, teste, migração ou governança que vai para o build.
   - **Parecer** do corretor e da marca: só como comentário no PR avaliado, sem PR próprio.
   - **Relatórios, catálogos de achados, backlog, critérios e roteiros de testes:** um PR só de documentação por dono, no fechamento da versão, e não um por rodada.
   - **Diário:** só dentro de um PR que já vai abrir, nunca sozinho.
   - Os PRs que já existem e já têm frase não são refeitos, porque refazer custa mais.
2. **Um push por PR.** Lint, typecheck e testes rodam na sessão antes do push. Se precisar de ajuste antes de abrir o PR, trabalhe em **rascunho** (o CI não roda) e tire do rascunho uma vez só, quando estiver pronto.
3. **Não juntar o main no branch sem necessidade.** O GitHub não exige branch atualizado. Só junte o main quando houver **conflito** ou quando o corretor pedir.
4. **Rerun:** só para falha de infraestrutura e uma vez só (regra que já existe; seguir à risca). Falha de código volta ao dono.
5. **Build do Android:** um só por versão, no fechamento, com o main verde e todos os pareceres fechados. Se falhar por código, não há nova tentativa sem correção conferida antes.
6. **Workflows manuais** (`producao-*`, carga, stack isolado, conector): só com pedido do dono do produto ou no rito de liberação da versão.

## Para o engenheiro-software, depois da tag v1.0.14 (não antes, para não atrasar a versão)
- O `ci.yml` ainda tem o agendado noturno (`cron '0 7 * * 1-5'`, 03h de Manaus, todos os pacotes). Cada execução custou de 37 a 68 min entre 8 e 13/11. Ele repete o que o push ao main já roda.
- **Pedido:** um PR de governança que tire esse agendado ou o deixe só semanal, mais o que mais o senhor achar que corta minutos sem tirar verificação. Mande antes a estimativa de minutos economizados por semana. O merge segue o rito de governança, com a frase do dono do produto.

## O que preciso do gerente
- Repasse estas regras a cada sessão que abrir e registre no quadro.
- Na próxima atualização, diga quantos PRs da v1.0.14 ainda precisam abrir e quais podem virar comentário ou PR único de documentação.
- **Não muda:** o merge continua um por vez, só com o CI do main verde, até o dono do produto decidir outra coisa.
