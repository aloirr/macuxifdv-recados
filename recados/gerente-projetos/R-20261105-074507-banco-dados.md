# T-0075: teste do DBaaS refeito para medir o que o admin sem SUPERUSER/BYPASSRLS permite, com caminhos alternativos (⚠️) e seção Plano B — pronto para disparar

## Contexto
T-0075. O run 42015544833 (commit 5d1f9d0) falhou porque o admin do DBaaS não tem SUPERUSER nem BYPASSRLS. A C2.2 deu "permission denied to alter role". A causa foi o `criarBanco` do @macuxi/db, que chama `garantirPapel` em db/src/papeis.ts. Nesse caminho, o papel macuxi_app já existia e recebeu `ALTER ROLE ... nosuperuser nobypassrls ... noreplication`. No PG 16, só um superusuário pode citar SUPERUSER, BYPASSRLS ou REPLICATION num ALTER ROLE, mesmo com o prefixo NO. O globalSetup da suíte caiu no mesmo erro.

## O que mudou (só db/dbaas/** e db/testes/dbaas.test.ts)
- **a. Base sem ALTER ROLE:** CREATE DATABASE direto. Papéis: papel novo = CREATE com os atributos; papel existente = só `LOGIN PASSWORD`, e os atributos são conferidos em pg_roles. A senha vai como verificador SCRAM calculado no cliente, então nunca chega em texto ao servidor (que tem pgaudit).
- **b. vector:** C1.2 tenta `CREATE EXTENSION vector` direto (pgextwlist). Se for negado e o SET ROLE mgc_superuser funcionar, tenta por ele e marca ⚠️.
- **c. X1.1:** atributos do mgc_superuser, opções da filiação do admin (ADMIN/INHERIT/SET) e SET ROLE. Já com o SET ROLE, mede is_superuser, BYPASSRLS, session_replication_role e CREATE ROLE BYPASSRLS. Tudo numa transação desfeita.
- **d. X1.2:** tenta `ALTER ROLE <admin> BYPASSRLS`, `CREATE ROLE ... BYPASSRLS` e `GRANT SET ON PARAMETER session_replication_role` (desfeito). X2 agora faz o SET real.
- **e. Migrações 0001..0027:**
  - Se o FORCE RLS barrar o dono, aplica o B1 e retoma (⚠️). Outro erro fica ❌.
  - C2.4–C2.6 seguem como estavam.
  - Seed (C2.7): roda como está; se falhar por privilégio, aplica o B1 e semeia de novo (⚠️).
  - C3.2 (DEFINER): mede pelo B1 e também "como está".
  - Novo B2: excluir_tenant da 0024 como está e, depois, DELETE em ordem de FK (o ciclo usuario/equipe é anulado antes), com a contagem do que sobrou. Transação desfeita.
  - Suíte: a base sai antes (L1) e os papéis são apagados para o globalSetup recriá-los pelo CREATE. Bloqueio de privilégio vira ⚠️; falha real fica ❌.
  - Se X3 mostrar que o servidor registra comandos de papel no log (log_statement/pgaudit.log), a suíte não roda e fica ⚠️, porque o papeis.ts manda a senha em texto. Para rodar mesmo assim: DBAAS_SUITE=forcar.
- **Plano B:** seção própria no relatório, com o que foi medido e com B0–B3 e o custo de cada um:
  - B0: papeis.ts sem ALTER de atributo. 1 arquivo, sem migração.
  - B1: papel macuxi_manutencao NOLOGIN herdado pelo migrador, com política `for all ... using (true)` em toda tabela com RLS. 1 migração; conferir-rls.sql e o teste de conformidade passam a exigir a política. Explica por que só `SET app.tenant_id` não basta: as políticas são `to macuxi_app`.
  - B2: excluir_tenant em ordem de FK, sem session_replication_role. 1 migração + demo.ts + lgpd-outbox.test.ts.
  - B3: pedir a vector no pgextwlist, se o CREATE direto falhar.
- **Código de saída 5** = critérios sem ❌, mas algum ⚠️ (aprovado só com o plano B). Pedido ao engenheiro-software no R-20261105-074431 para o resumo do workflow traduzir o 5.
- **Limpeza** (sempre, no finally e no --so-limpar): L1 base do teste, L2 bases criadas pela suíte, L3 papéis macuxi_dbaas_*, macuxi_app e macuxi_worker (DBAAS_MANTER_PAPEIS=1 mantém os dois últimos).
