## Contexto

## O que preciso
Nada muda no contrato `core.inicio@1`: proponho que o fallback preencha o campo que já existe, `positivacao: { ate_ontem, hoje }`.
1. **Leitura (fallback do Início, Vendedor desligado)**, na transação do comTenant (papel macuxi_app, RLS vale):
   `select usuario_id, ate_ontem, hoje, mes from core.positivacao_do_mes($1::uuid[], $2, $3::date)` com `paraConsultar`, `periodo` ('AAAA-MM') e `dia` (hoje no fuso do tenant; nulo = o banco calcula pelo fuso do tenant).
   Uma linha por usuário pedido. Cada cliente conta UMA vez no mês, no primeiro dia em que foi positivado: `ate_ontem` = primeiro dia < hoje; `hoje` = primeiro dia = hoje (os NOVOS hoje, igual ao `realizadoPartido`, RN-CORE-20/26); `mes` = todos do mês.
   **null nos três = sem fonte** → mantenha `positivacao = null` (a regra "sem fonte não entra nas metas do dia" segue). Com fonte e sem cliente no mês = 0 (mês novo zera).
2. **Escrita (o consumidor que alimenta o read-model, quando existir)**: gravar `clientes_positivados_ids uuid[]` (QUAIS clientes, sem repetição, só do próprio tenant) junto com `clientes_positivados` do dia. O CHECK `indicador_diario_clientes_positivados_ids_coerente` exige lista de 1 dimensão, sem nulo e `clientes_positivados = cardinality(lista)`; lista nula continua valendo (não apurado). Cancelamento que tira o cliente do dia: regravar lista e contagem do dia.
3. Espelho Drizzle `indicadorDiario.clientes_positivados_ids` já está em modules/core/db/nuvem.ts. O pull (`TABELAS_SYNC.indicador_diario`) lista as colunas: a lista só vai ao aparelho se você quiser a conta offline (o app pode repetir a mesma regra com a lista).
