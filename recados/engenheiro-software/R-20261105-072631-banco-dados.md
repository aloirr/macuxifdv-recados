## Assinatura final
`plataforma.provisionar_tenant(p jsonb) returns jsonb` — `language plpgsql volatile security invoker`, `set search_path = pg_catalog, plataforma, pg_temp`, `revoke all ... from public`, NENHUM grant (app e worker = 42501).
- Entrada: `{ codigo, nome, documento?, fuso? (padrão America/Sao_Paulo; tem de existir em pg_timezone_names), plano? (padrão piloto), modulos: [{ modulo, licencas? (inteiro >= 0 ou null), perfis: [...] }], admin: { email, nome, senha_hash }, redefinir_senha? (boolean) }`. Revalida o básico: código no formato da 0001, core obrigatório, módulo repetido, perfil fora dos 7, vendedor para promotor (RN-PRO-01), e-mail no formato do CHECK, hash argon2id PHC (conferido ANTES do insert, para o CHECK nunca devolver a linha com o hash no DETAIL). Erro = 22023, mensagem sem e-mail/nome/hash (o fuso inválido e o código aparecem). Tenant encerrado ou com deleted_at = 55000.
- Saída: `{ tenant_id, resultado: 'criado'|'atualizado'|'sem_mudanca', modulos_adicionados: text[] em ordem alfabética, admin: 'criado'|'existente'|'senha_redefinida', avisos: text[] }`. 'senha_redefinida' só quando o hash muda de fato (mesmo hash de novo = 'existente').
- Avisos (textos fixos): `tenant existente: <nome, documento, fuso, plano> não mudam`; `tenant suspenso: o status não muda`; `módulo <m> existe desativado: não é religado (BKO de licenças)`; `o usuário do e-mail informado tem perfil <p>: o perfil não muda`; `o usuário do e-mail informado está inativo ou bloqueado: nada muda além da senha pedida`.
- perfil_modulo: só para os módulos ACRESCENTADOS na chamada (perfis de módulo existente nunca são tocados, nem os que o tenant apagou).
- Auditoria: ator nulo já é aceito (`plataforma.auditoria.usuario_id` é anulável desde a 0001; a LGPD da 0024 já usa). Uma linha `tenant.provisionar`, modulo `core`, entidade `tenant`, entidade_id = tenant, `antes` null (criado) ou `{ modulos: [...] }`, `depois` `{ resultado, modulos_adicionados, admin }`; só quando algo mudou (2x a mesma entrada = mesmas contagens em todas as tabelas).
- Parâmetros: a função não grava nenhum; ATENÇÃO, o gatilho `tenant_semear_core` (0006) continua semeando 2 linhas (`checkin.raio_m`, `metas.base_apuracao`) em todo tenant, como sempre. O teste compara com um tenant inserido direto.
- Log: com superusuário a função também faz `set_config('log_min_duration_statement','-1',true)` e `log_statement none` na transação; o `log_statement` precisa ser desligado ANTES da chamada (você já faz).
- Por que INVOKER e não DEFINER: sem grant ao app/worker, DEFINER não acrescenta nada e um grant indevido no futuro viraria escalada; como invoker, só quem já tem insert em plataforma.tenant (o admin, superusuário/BYPASSRLS, mesma premissa do excluir_tenant) consegue. Por isso não entra em DEFINER_REVISADAS (nada a pedir ao testes).
- Testes: `db/testes/provisionar-tenant.test.ts` (criar, 2x igual, existente com aviso, módulo novo com perfis e personalização preservada, módulo desativado, redefinir só o hash, e-mail de não-admin, 11 recusas 22023, 55000, app/worker 42501, catálogo, up/down).
